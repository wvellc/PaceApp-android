# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product context (read first)

PaceApp is a running/walking pace-tracking product with **three codebases** that must stay in sync. This repo is the **Android companion app**; the other two are checked out as siblings under `/Volumes/WveBhavesh/WVE/PaceApp/`:

- **`PaceApp-Garmin`** (Monkey C, branch `V2.3`) — the **source of truth** for the domain model, event lifecycle, and the Bluetooth (ConnectIQ) **wire protocol**. The watch defines the message shapes; the phone apps conform. **Do not invent new sync message shapes** — mirror the watch. Its sync logic lives in `source/Helpers/EventSync.mc`.
- **`PaceApp-ios`** (SwiftUI + Firebase, branch `Firebase-Integration`) — the **reference implementation** for phone behavior: screens, Firestore schema, Firebase Auth, and how a phone speaks the sync protocol. When adding a feature, match iOS.
- **`PaceApp-android`** (this repo) — mirror iOS behavior and the Garmin protocol; follow the Android conventions below.

Both phone apps share **one Firebase project (`thepaceapp`)** and read/write the **same Firestore documents**. Any change to the Firestore schema or the wire format must preserve cross-app/backward compatibility.

## Build & run

There is **no Java on PATH** in the default shell. Use the Gradle-managed JDK 17 and the Android SDK explicitly:

```bash
export JAVA_HOME="$HOME/.gradle/jdks/eclipse_adoptium-17-aarch64-os_x.2/jdk-17.0.19+10/Contents/Home"
export ANDROID_HOME="/Volumes/WveBhavesh/developer/Library/Android/sdk"

./gradlew :app:compileDebugKotlin      # fast compile check after edits
./gradlew :app:assembleDebug           # build the debug APK
./gradlew :app:installDebug            # install on a connected device/emulator
./gradlew :app:lintDebug               # Android Lint
```

- `gradlew` may need `chmod +x` (or invoke via `sh gradlew`).
- The project is on an **external volume** (`/Volumes/WveBhavesh`). Do **not** run Bash with the sandbox disabled against this path — macOS revokes removable-volume access for the whole process and you lose all file access until Claude Code is restarted.
- **Secrets:** the Google Maps key is injected via the secrets-gradle-plugin from `secrets.properties` (fallback `local.defaults.properties`, key `MAPS_API_KEY`). Firebase requires `app/google-services.json` (project `thepaceapp`); phone-number auth also requires the app's SHA-1/SHA-256 registered in the Firebase console.
- No dedicated test suite is established; `./gradlew test` / `connectedDebugAndroidTest` run the standard Gradle test tasks if/when tests are added.

## Scaffolding new screens

Every feature screen follows a fixed MVI shape generated by `generate_screen.sh`:

```bash
./generate_screen.sh net.paceapp.features.<feature>.<screen> <ScreenName>
```

It emits `<Name>Contract.kt` (State/Event/Effect), `<Name>ViewModel.kt` (extends `BaseViewModel`), `<Name>Screen.kt` (Compose entry, collects state + handles effects), `components/<Name>Content.kt` (stateless UI), and `navigation/<Name>Navigation.kt` (`@Serializable` route object + `NavGraphBuilder` extension). Use it rather than hand-rolling screens.

## Module architecture

Three Gradle modules (`settings.gradle.kts`):

- **`:app`** (`net.paceapp`) — all feature screens, the Garmin/ConnectIQ sync layer, the Firestore data layer, and DI wiring.
- **`:core-network`** (`com.wvelabs.core_network`) — app-agnostic networking/session infra: `NetworkResult<T>`, `ErrorHandler`/`NetworkError`, `AuthInterceptor` (Bearer + global 401 via `SessionListener`), `SessionContracts` (implemented by `:app`), `CryptoManager`, `AppLogger`, DataStore base, and the timer engine. **Note:** despite this REST scaffold, the actual data backend is Firebase/Firestore, not a REST API.
- **`:core-ui`** (`com.wvelabs.core_ui`) — the MVI base (`CoreViewModel`/`BaseViewModel`), the global alert system, and shared Compose components.

Kotlin 2.3 · Jetpack Compose · Hilt DI (KSP) · Navigation-Compose · Coroutines/Flow · DataStore. `minSdk 24`, `targetSdk 36`, JVM 17.

### MVI (from `:core-ui`)

Unidirectional flow per screen: `ViewState` (single source of truth) ← `ViewEvent` (user actions) → `ViewSideEffect` (one-time nav/toasts). ViewModels extend `BaseViewModel`, mutate via `setState { copy(...) }`, dispatch effects via `setEffect { ... }`, and run async work via `safeLaunch`. Never hoist screen state into `@State`-equivalents outside the ViewModel.

### Global alerts + `MainActivity` wrapping order

Alerts are fire-and-forget: call `AppAlerts.showToast(text, type)` from anywhere (ViewModel/repo). For overlays to float above all screens, `MainActivity` must wrap in this exact order: **Theme → `AppAlertContainer` → `AppNavHost`** (see `CORE_README.md`).

### Navigation

Type-safe: each screen exposes a `@Serializable` route object and a `NavGraphBuilder` extension; `navigation/AppNavHost.kt` is the central registry. Auth routing is decided by `AuthRouteManager` / `AuthDestination` (new user → build-profile, else → tabhost).

## Garmin sync layer (`app/.../core/garmin/`)

This is the heart of the app and mirrors iOS's `ConnectIQManager`:

- **`GarminConnectHelper`** — thin wrapper over the ConnectIQ SDK (device/app enumeration, register for events, send/receive messages as `List<Any>` of `Map`s).
- **`GarminDeviceManager`** (singleton) — device lifecycle + connection state; exposes `incomingMessages`, `activeDevice`, and an `onAppReady` hook; `sendMessageToWatch(payload)`.
- **`EventSyncManager`** (singleton) — the sync engine. `handleSyncMessage` dispatches watch commands; `create/finish/delete Event` + `sendSettings` push to the watch. On app-ready it fires `sync_request`.

**Wire protocol (the contract — conform exactly):** every message is `{ "command": <str>, "source": "watch"|"phone", ... }`. Commands: `sync_request` (reply with `sync_all`), `sync_all` (one-way, no reply — replying loops), `create_event`/`finish_event` (`{id, event}`), `delete_event` (`{id}`), `sync_settings` (`{settings}`). Merge order on receiving a full sync: **deletes → completed → active → settings → persist**. Event wire fields are stringly-typed: `date` = `"MMM/d/yyyy"`, `distance` = `"5.00"`, `goal`/`actualTime` = `"HH:MM:SS"`, `timeVar` = signed `"+/-HH:MM:SS"`. Do **not** port the watch's storage caps (max 5 active / 3 completed) to the phone — the phone is the full archive.

## Firestore data layer (`app/.../core/data/firestore/`)

Bridges the ConnectIQ wire format ↔ Firestore, matching the iOS schema field-for-field so both phones interoperate over the shared backend:

- **`EventDocumentMapper`** is the **single parse path** for raw `Map<String, Any?>` wire payloads → `EventDocument` (and back via `connectIQPayload`). Nothing else should parse event dicts. `ActivityTypeWire` maps activity strings to the canonical Firestore value (`Run`/`Walking`/`Cycling`/`Other`) and the watch value (`Run`/`Walk`/`Cycling`/`Other`).
- **`FirestoreEventRepository`** (`EventRepository`) — `observeActiveEvents`/`observeCompletedEvents` (active has **no date filter** — overdue-but-active events stay visible), `upsert` (preserves **write-once `id`/`source`/`createdAt`** by reloading the doc), `softDelete` (`status="deleted"` + `deletedAt`), and `fetchAllEventPayloads` to seed the watch.
- **`FirestoreUserProfileRepository`** (`UserProfileRepository`) — `users/{uid}` profile + settings (`gait` map, `intervalVibrate`/`intervalBeep`, `distanceUnit`). **Gait unit boundary:** the watch speaks `ft`/`m` + string numbers; Firestore/app store `"Feet"`/`"Meters"` + `Double` — convert only at the BLE boundary.

Firestore doc id = `String(event.id)`; `id` is also stored as a field. Firestore rules require `auth.uid`, so Firebase Auth is a hard prerequisite for any cloud data. `EventRepository`/`UserProfileRepository` are interfaces bound in `di/RepositoryModule.kt`; `AnalyticsRepository` and `FavoriteRepository` are **concrete `@Singleton` classes** (injected directly, no binding). `FirebaseAuth`/`FirebaseFirestore` (with offline persistence) come from `di/FirebaseModule.kt`. Note the package-internal `Task<T>.await()` + `QuerySnapshot.toEventDocuments()` extensions in `FirestoreExt.kt` — reuse them for any new suspend Firestore call rather than adding the `kotlinx-coroutines-play-services` dependency.

To turn a Firestore `EventDocument` into a UI row, go through `core/mappers/EventDocumentUiMapper.toActivityModel(doc)` then the existing `ActivityToUiModelMapper` — the single documents→list-row path shared by Home/History/Favorites.

## Authentication

`AuthManager` (`app/.../core/auth/AuthManager.kt`) wraps `FirebaseAuth` for **phone OTP** (`PhoneAuthProvider`, needs an `Activity` — passed through `LoginContract.Event.OnLoginClick`) and **passwordless email link** (`sendSignInLinkToEmail` / `signInWithEmailLink`; the incoming App Link is completed in `MainActivity.handleEmailSignInLink`). On any sign-in it fetch-or-creates `users/{uid}` and mirrors identity into `AppSessionManager` so the existing `AuthRouteManager` (session token + `isProfileComplete`) still drives routing (Splash → BuildProfile/TabHost). Firestore rules require `auth.uid`, so a signed-in user is a prerequisite for all cloud reads/writes; the `EventSyncManager` Firestore write-through is a no-op until then.

Done: Firebase onboarding, Firebase Auth (phone + email link), the Firestore data layer, the BLE↔Firestore write-through bridge, all screens re-sourced from Firestore (Home/History/EventDetails/Edit/Duplicate/Settings/Gait/EditProfile/Profile), Analytics (`AnalyticsRepository` + `AnalyticsAggregator`, period bucketing mirroring iOS) and Favorites (`FavoriteRepository` over the `favorites` collection), and a mock Notifications module with its entry point hidden (parity with iOS — no FCM).

Known follow-up: Favorites has a list + repository but no "favorite" toggle entry point yet (iOS toggles from EventDetails).
