# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product context (read first)

PaceApp is a running/walking pace-tracking product with **three codebases** that must stay in sync. This repo is the **Android companion app**; the other two are checked out as siblings under `/Volumes/WveBhavesh/WVE/PaceApp/`:

- **`PaceApp-Garmin`** (Monkey C, branch `V2.3`) — the **source of truth** for the domain model, event lifecycle, and the Bluetooth (ConnectIQ) **wire protocol**. The watch defines the message shapes; the phone apps conform. **Do not invent new sync message shapes** — mirror the watch. Its sync logic lives in `source/Helpers/EventSync.mc`.
- **`PaceApp-ios`** (SwiftUI + Firebase, branch `Firebase-Integration`) — the **reference implementation** for phone behavior: screens, Firestore schema, Firebase Auth, and how a phone speaks the sync protocol. When adding a feature, match iOS.
- **`PaceApp-android`** (this repo) — mirror iOS behavior and the Garmin protocol; follow the Android conventions below.

Both phone apps share **one Firebase project (`thepaceapp`)** and read/write the **same Firestore documents**. Any change to the Firestore schema or the wire format must preserve cross-app/backward compatibility.

## Build & run

There is **no Java on PATH** in the default shell. Point `JAVA_HOME` at an installed JDK 17 and set the Android SDK explicitly. Resolve the JDK dynamically (works across JDK updates and if the Gradle-managed `~/.gradle/jdks` toolchain gets cleaned):

```bash
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"   # e.g. /Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home
export ANDROID_HOME="/Volumes/WveBhavesh/developer/Library/Android/sdk"

./gradlew :app:compileDebugKotlin      # fast compile check after edits
./gradlew :app:assembleDebug           # build the debug APK
./gradlew :app:installDebug            # install on a connected device/emulator
./gradlew :app:lintDebug               # Android Lint
```

- `gradlew` may need `chmod +x` (or invoke via `sh gradlew`).
- The project is on an **external volume** (`/Volumes/WveBhavesh`). Do **not** run Bash with the sandbox disabled against this path — macOS revokes removable-volume access for the whole process and you lose all file access until Claude Code is restarted.
- **Secrets:** the Google Maps key is injected via the secrets-gradle-plugin from `secrets.properties` (fallback `local.defaults.properties`, key `MAPS_API_KEY`). Firebase requires `app/google-services.json` (project `thepaceapp`); phone-number auth also requires the app's SHA-1/SHA-256 registered in the Firebase console.
- No dedicated test suite is established; `./gradlew test` / `connectedDebugAndroidTest` run the standard Gradle test tasks if/when tests are added.

## Scaffolding new screens

Every feature screen follows a fixed MVI shape generated by `generate_screen.sh`:

```bash
./generate_screen.sh net.paceapp.features.<feature>.<screen> <ScreenName>
```

It emits `<Name>Contract.kt` (State/Event/Effect), `<Name>ViewModel.kt` (extends `BaseViewModel`), `<Name>Screen.kt` (Compose entry, collects state + handles effects), `components/<Name>Content.kt` (stateless UI), and `navigation/<Name>Navigation.kt` (`@Serializable` route object + `NavGraphBuilder` extension). Use it rather than hand-rolling screens.

## Module architecture

Three Gradle modules (`settings.gradle.kts`):

- **`:app`** (`net.paceapp`) — all feature screens, the Garmin/ConnectIQ sync layer, the Firestore data layer, and DI wiring.
- **`:core-network`** (`com.wvelabs.core_network`) — app-agnostic networking/session infra: `NetworkResult<T>`, `ErrorHandler`/`NetworkError`, `AuthInterceptor` (Bearer + global 401 via `SessionListener`), `SessionContracts` (implemented by `:app`), `CryptoManager`, `AppLogger`, DataStore base, and the timer engine. **Note:** despite this REST scaffold, the actual data backend is Firebase/Firestore, not a REST API.
- **`:core-ui`** (`com.wvelabs.core_ui`) — the MVI base (`CoreViewModel`/`BaseViewModel`), the global alert system, and shared Compose components.

Kotlin 2.3 · Jetpack Compose · Hilt DI (KSP) · Navigation-Compose · Coroutines/Flow · DataStore. `minSdk 24`, `targetSdk 36`, JVM 17.

### MVI (from `:core-ui`)

Unidirectional flow per screen: `ViewState` (single source of truth) ← `ViewEvent` (user actions) → `ViewSideEffect` (one-time nav/toasts). ViewModels extend `BaseViewModel`, mutate via `setState { copy(...) }`, dispatch effects via `setEffect { ... }`, and run async work via `safeLaunch`. Never hoist screen state into `@State`-equivalents outside the ViewModel.

### Global alerts + `MainActivity` wrapping order

Alerts are fire-and-forget: call `AppAlerts.showToast(text, type)` from anywhere (ViewModel/repo). For overlays to float above all screens, `MainActivity` must wrap in this exact order: **Theme → `AppAlertContainer` → `AppNavHost`** (see `CORE_README.md`).

### Navigation

Type-safe: each screen exposes a `@Serializable` route object and a `NavGraphBuilder` extension; `navigation/AppNavHost.kt` is the central registry. Auth routing is decided by `AuthRouteManager` / `AuthDestination` (new user → build-profile, else → tabhost).

## Garmin sync layer (`app/.../core/garmin/`)

This is the heart of the app and mirrors iOS's `ConnectIQManager`:

- **`GarminConnectHelper`** — thin wrapper over the ConnectIQ SDK (device/app enumeration, register for events, send/receive messages as `List<Any>` of `Map`s).
- **`GarminDeviceManager`** (singleton) — device lifecycle + connection state; exposes `incomingMessages`, `activeDevice`, and an `onAppReady` hook; `sendMessageToWatch(payload)`.
- **`EventSyncManager`** (singleton) — the sync engine. `handleSyncMessage` dispatches watch commands; `create/finish/delete Event` + `sendSettings` push to the watch. On app-ready it fires `sync_request` **and `request_settings`** (so the watch pushes its height/weight/gait).

**Wire protocol (the contract — conform exactly):** every message is `{ "command": <str>, "source": "watch"|"phone", ... }`. Commands: `sync_request` (reply with `sync_all`), `sync_all` (one-way, no reply — replying loops), `create_event`/`finish_event` (`{id, event}`), `delete_event` (`{id}`), `sync_settings` (`{settings}`), `request_settings` (phone→watch; watch replies `sync_settings`). Merge order on receiving a full sync: **deletes → completed → active → settings → persist**. Event wire fields are stringly-typed: `date` = `"MMM/d/yyyy"`, `distance` = `"5.00"`, `goal`/`actualTime` = `"HH:MM:SS"`, `timeVar` = signed `"+/-HH:MM:SS"`. Do **not** port the watch's storage caps (max 5 active / 3 completed) to the phone — the phone is the full archive.

**Settings / body metrics (mirror iOS `83ea138`, with a gait-override fix):** the watch settings payload also carries `user_height` (cm), `user_weight` (**grams**), and step lengths in **mm**. On an incoming `sync_settings`, the app re-derives gait from height via `GaitStrideCalculator` (walking ×0.413, running ×0.65 m) **only when the height actually changed** (compared against the stored `heightCm` before overwriting it) — then it saves the derived gait + `heightCm`/`weightKg` and pushes the computed mm step lengths back. When the height is unchanged it **respects the gait the watch reports and does NOT push back**, so a manual gait change made on the watch sticks instead of being overwritten. (This diverges from iOS, which always re-derives from height — a deliberate fix so watch-side gait edits aren't clobbered.) `EventSyncManager.getSettingsPayload` emits `walking_step_length`/`running_step_length` (Int mm) alongside the 6 gait/alert keys.

## Firestore data layer (`app/.../core/data/firestore/`)

Bridges the ConnectIQ wire format ↔ Firestore, matching the iOS schema field-for-field so both phones interoperate over the shared backend:

- **`EventDocumentMapper`** is the **single parse path** for raw `Map<String, Any?>` wire payloads → `EventDocument` (and back via `connectIQPayload`). Nothing else should parse event dicts. `ActivityTypeWire` maps activity strings to the canonical Firestore value (`Run`/`Walking`/`Cycling`/`Other`) and the watch value (`Run`/`Walk`/`Cycling`/`Other`).
- **`FirestoreEventRepository`** (`EventRepository`) — `observeActiveEvents`/`observeCompletedEvents` (active has **no date filter** — overdue-but-active events stay visible), `upsert` (preserves **write-once `id`/`source`/`createdAt`** by reloading the doc), `softDelete` (`status="deleted"` + `deletedAt`), and `fetchAllEventPayloads` to seed the watch.
- **`FirestoreUserProfileRepository`** (`UserProfileRepository`) — `users/{uid}` profile + settings (`gait` map, `intervalVibrate`/`intervalBeep`, `distanceUnit`, and watch-sourced `heightCm`/`weightKg` via `updateBodyMetrics`; `deleteUser` for account deletion). **Gait unit boundary:** the watch speaks `ft`/`m` + string numbers; Firestore/app store `"Feet"`/`"Meters"` + `Double` — convert only at the BLE boundary. `GaitStrideCalculator` (`core/garmin/`) holds the height→gait math + Feet/Meters↔mm conversions.

Firestore doc id = `String(event.id)`; `id` is also stored as a field. Firestore rules require `auth.uid`, so Firebase Auth is a hard prerequisite for any cloud data. `EventRepository`/`UserProfileRepository` are interfaces bound in `di/RepositoryModule.kt`; `AnalyticsRepository` and `FavoriteRepository` are **concrete `@Singleton` classes** (injected directly, no binding). `FirebaseAuth`/`FirebaseFirestore` (with offline persistence) come from `di/FirebaseModule.kt`. Note the package-internal `Task<T>.await()` + `QuerySnapshot.toEventDocuments()` extensions in `FirestoreExt.kt` — reuse them for any new suspend Firestore call rather than adding the `kotlinx-coroutines-play-services` dependency.

To turn a Firestore `EventDocument` into a UI row, go through `core/mappers/EventDocumentUiMapper.toActivityModel(doc)` then the existing `ActivityToUiModelMapper` — the single documents→list-row path shared by Home/History/Favorites.

## Authentication

`AuthManager` (`app/.../core/auth/AuthManager.kt`) wraps `FirebaseAuth` for **phone OTP** (`PhoneAuthProvider`, needs an `Activity` — passed through `LoginContract.Event.OnLoginClick`) and **passwordless email link** (`sendSignInLinkToEmail` / `signInWithEmailLink`; the incoming App Link is completed in `MainActivity.handleEmailSignInLink`, which shows the `Authenticating` screen via `emailLinkPhase`). On any sign-in it fetch-or-creates `users/{uid}` and mirrors identity into `AppSessionManager` so the existing `AuthRouteManager` (session token + `isProfileComplete`) still drives routing (Splash → BuildProfile/TabHost). Firestore rules require `auth.uid`, so a signed-in user is a prerequisite for all cloud reads/writes; the `EventSyncManager` Firestore write-through is a no-op until then.

- **Phone-OTP navigation:** `onCodeSent` delivers the `verificationId`, which is carried to the OTP screen as a **nav-route argument** (`VerifyOtpRoute.verificationId`) — robust across the reCAPTCHA activity round-trip. Phone auth requires the running build's **SHA-1 + SHA-256 in the Firebase console** (separate from `assetlinks.json`); a missing cert surfaces as `onVerificationFailed` (the callbacks log `[Auth] …` for diagnosis).
- **Logout must sign out Firebase.** `SettingsViewModel.handleLogout` calls `authManager.signOut()` (`auth.signOut()` + `clearSession()`) before the session-expired nav — clearing only the local session leaves `auth.currentUser` set, so a later phone-OTP login latches onto the stale account on the Verify screen (skipping the OTP). `VerifyOtpViewModel` deliberately auto-routes when `isSignedIn` (the auto-verified-SMS path), which is why a stale Firebase user must not survive logout.
- **Account deletion + reauth** (`deleteAccount` / `reauthenticateWith{Phone,EmailLink}`, `authProviderKind`) — matches iOS. Firebase requires a recent login, so the Settings delete flow reauthenticates (phone OTP or email link) first, then deletes in order **disconnect watch → disconnect Strava (`StravaManager.disconnectForAccountDeletion`, best-effort server revoke) → events → favorites → `users/{uid}` → Auth user → sign out → clear session** (cloud cleanup best-effort; `user.delete()` propagates). The reauth popups (`components/DeleteReauthOverlays.kt`) render on a dimmed full-screen scrim; the email-link reauth return is handled in `MainActivity` guarded by `isReauthenticatingForDeletion`.
- **Remote deletion / session validity.** An `AuthManager` `FirebaseAuth.AuthStateListener` (guarded by `hadSignedInUser` against the cold-start transient null) plus a resume-time forced token refresh (`MainActivity.onResume` → `verifyAccountStillValid()`) detect an account deleted/disabled on another device and route to Login. `verifyAccountStillValid(): Boolean` also **guards every write** — event create/duplicate/edit/delete, profile edit, and the distance-unit setting — so a dead session is signed out instead of appearing to save (mirrors iOS `38b4a9d`/`97bbfcf`). The session-expired path routes to Login and shows a **toast** ("Your session has timed out…"), NOT a dialog: a Material3 dialog opens a separate input window that, torn down while the nav back-stack cleared, stranded touch input.
- **Profile persistence + cross-device live sync.** Signup writes `firstName`/`lastName`/`gender` to `users/{uid}` (`UserProfileRepository.updateProfile`; gender as `"Male"/"Female"/"Other"`, iOS `Gender.rawValue`) — previously it stayed in the local session only. `ProfileSessionSync` (`core/data/`) live-mirrors `users/{uid}` → the local session via `UserDocument.mergeInto(UserData)` (preserving `loginType`/`countryCode` the doc lacks), so a profile edit on another device refreshes Profile/Home/EditProfile live; it's started/stopped from AuthManager's auth-state listener.
- **`AuthErrorMapper`** turns raw `FirebaseAuthException`/network errors into friendly messages — use it for all auth error toasts.
